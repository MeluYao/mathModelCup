# 数学建模团队 AI 协作指南

本指南供不熟悉 Git 的团队成员使用。请把它放进 Codex 或 Claude Code 的工作目录，并让 AI 在开始工作前完整阅读。成员只需要说明数学问题、分析目标和期望结果；Git、环境检查、测试与 Pull Request 可以交给 AI 处理。

## 先把这段话发给 AI

```text
请先完整阅读 AI_COLLABORATION_GUIDE.md 和项目 README.md，并检查当前仓库状态。
你负责协助我完成 Git 操作、环境管理、代码实现和测试，但必须遵守以下规则：
1. 赛题资料、原始数据、评估报告、Word 文档、临时文件和运行输出不得加入 Git。
2. 不要直接修改 main；先同步 main，再创建描述本次工作的功能分支。
3. 在提交前向我展示 git status、计划提交的文件和测试结果。
4. 删除文件、放弃本地修改、强制推送、合并 PR、发送邀请、修改权限、公开仓库或上传资料前，必须说明影响并取得我的明确确认。
5. 遇到冲突或测试失败时先诊断原因，不要强行覆盖。
完成后请告诉我：改了什么、测试是否通过、提交号、分支名和 PR 链接。
```

Codex 和 Claude Code 都可以使用这段提示词。若 AI 能自动读取工作目录中的说明文件，也仍建议在首次会话中明确要求它阅读本指南。

## 成员与 AI 的分工

成员负责：

- 说明数学问题、假设、约束、数据含义和成功标准。
- 判断模型是否符合题意，核对结论是否具备数学与业务解释。
- 确认高影响操作，例如推送、合并、删除、权限变更和对外发布。
- 审阅 AI 给出的结果摘要、图表和 Pull Request。

AI 负责：

- 检查仓库状态和已有说明。
- 同步代码、创建分支、编辑文件、运行测试、提交与准备 Pull Request。
- 在操作前说明目的，在操作后报告结果。
- 发现风险时停止并向成员询问，不猜测、不覆盖他人的工作。

AI 不得自行：

- 将私有资料、赛题文件、数据或输出加入 Git。
- 使用 `git reset --hard`、强制推送或删除重要文件。
- 直接向 `main` 推送未经审查的工作。
- 发送邀请、调整仓库权限、公开仓库或合并 Pull Request。
- 把密码、令牌、邮箱验证码或其他凭据写入代码和文档。

## 本仓库不能上传的内容

下列内容只保留在本地，不得加入 Git：

- `A题/`、`B题/`、`C题/`、`D题/`、`F题/`
- `评估报告/`
- 所有 `.docx` 赛题文档
- `tmp/`
- `data/raw/`、`data/processed/` 中的实际数据
- `outputs/` 中的图表、模型、报告和其他运行产物
- 本地 Conda 或虚拟环境目录
- 密码、访问令牌、密钥和个人敏感信息

这些规则已经写入 `.gitignore`，但 AI 在每次提交前仍必须检查暂存清单。

可直接对 AI 说：

```text
请检查 git status 和暂存清单，确认没有赛题资料、数据、Word 文档、tmp 或 outputs 内容。只报告检查结果，不要推送。
```

## 每次工作的标准流程

### 1. 开始任务

告诉 AI 本次目标和交付物，例如：

```text
请先读取协作指南和 README，检查仓库状态并同步 main。
然后为“建立时间序列基线模型”创建一个功能分支。
先给出简短计划，不要修改 main，不要上传任何赛题或数据文件。
```

AI 应完成：

1. 检查未提交修改，避免覆盖成员已有工作。
2. 拉取远程 `main` 的最新版本。
3. 创建语义清晰的分支，例如 `model/time-series-baseline`、`analysis/data-quality`。
4. 说明它准备修改哪些文件。

### 2. 开发与数学验证

探索性分析放在 `notebooks/`。可复用、稳定的代码放在 `src/math_model_cup/`，可执行入口放在 `scripts/`，测试放在 `tests/`。

建议成员提供给 AI 的信息：

- 变量和单位的定义。
- 数据缺失、异常值和约束条件。
- 模型假设及不可违反的数学条件。
- 评价指标和基准方案。
- 需要生成的图表、表格或结论。

示例：

```text
请建立一个最简单的可解释基线。先写测试，再实现稳定代码。
探索过程可以放 notebooks，但最终计算逻辑必须进入 src/math_model_cup。
不要读取或提交赛题目录；请使用我明确指定的本地数据路径。
```

### 3. 环境与测试

项目使用 Python 3.11 和 Conda。让 AI 优先读取 `environment.yml`，不要随意创建另一套依赖配置。

首次创建环境：

```text
请根据 environment.yml 创建或检查 math-model-cup Conda 环境。
如果安装失败，先诊断网络、渠道或版本问题，不要删除其他 Conda 环境。
```

运行示例与测试：

```text
请在 math-model-cup 环境中运行示例和全部测试。
把执行命令、通过数量、失败信息和警告摘要告诉我，不要为了通过测试而删除测试。
```

### 4. 提交前检查

让 AI 在提交前执行检查，但此时不要推送：

```text
请运行全部相关测试，然后展示 git status 和即将提交的文件。
确认没有赛题、数据、评估报告、Word 文档、tmp 或 outputs 内容。
给出建议提交信息，等待我确认后再提交和推送。
```

成员应确认：

- 文件清单只包含代码、测试、配置和必要文档。
- 测试结果与 AI 的描述一致。
- 分支不是 `main`。
- 提交信息准确说明本次变化。

### 5. 提交、推送和 Pull Request

成员确认后，可以说：

```text
确认提交并推送当前功能分支，然后创建 Pull Request 到 main。
PR 中写清问题、方法、验证结果、主要假设和已知限制。
创建后把分支名、提交号和 PR 链接发给我；不要自行合并。
```

团队应在 GitHub 上审阅 Pull Request。至少一名其他成员检查数学方法、结果解释和代码变更后，再由有权限的人确认合并。

## 常用任务提示词

### 让 AI 解释当前状态

```text
请用不需要 Git 基础的方式解释当前分支、未提交修改、与远程仓库的差异，以及下一步建议。只读检查，不要修改任何内容。
```

### 请求数学建模实现

```text
目标是【填写目标】。
已知变量与单位是【填写定义】，约束是【填写约束】，评价指标是【填写指标】。
请先复述假设和成功标准，再给出方案；经我确认后在新分支实现、测试并准备 PR。
```

### 请求结果复核

```text
请独立检查模型假设、维度与单位、边界条件、数据泄漏、指标计算和结论是否一致。
发现问题时指出证据，不要直接改代码；先给出审查报告。
```

### 请求生成可提交的结果

```text
请把稳定的计算逻辑整理到 src/math_model_cup，把测试放到 tests。
不要提交原始数据、生成图表或赛题资料。
运行测试并展示 git status，等待我确认后再提交。
```

## 遇到问题时怎么让 AI 处理

### 合并冲突

不要让 AI 盲目选择一方或覆盖文件。使用：

```text
当前出现合并冲突。请先列出冲突文件，解释双方修改意图和可能影响。
不要执行强制覆盖、reset --hard 或推送。给出逐文件解决建议，等待我确认。
```

### 误暂存了不应上传的文件

使用：

```text
我可能误暂存了赛题、数据或输出文件。请检查暂存区，只把这些文件从暂存区移除，不要删除本地文件。
然后确认 .gitignore 是否能防止再次暂存，并展示新的暂存清单。
```

### Conda 环境创建失败

使用：

```text
Conda 环境创建失败。请读取完整错误，检查 conda 版本、channel、网络和依赖冲突。
先说明根因和最小修复方案，不要删除 base 或其他现有环境，也不要改用未说明的 Python 版本。
```

### 测试失败

使用：

```text
测试失败。请先复现并定位根因，区分代码缺陷、环境问题和测试本身的问题。
不要跳过或删除失败测试。修复前向我说明证据与拟议变更，修复后重跑相关测试和完整测试。
```

### AI 准备执行高风险操作

如果 AI 提到删除、强制推送、重置、公开仓库、修改权限或合并，成员应先问：

```text
请停止执行。先说明这个操作会改变什么、影响哪些文件或人员、是否可恢复，以及更安全的替代方案。没有我的明确确认不要继续。
```

## 提交前最终清单

让 AI 逐项回答：

- 当前是否位于功能分支，而不是 `main`？
- 是否已同步最新 `main`？
- 是否仅修改了本任务需要的文件？
- 是否确认赛题、数据、Word 文档、临时文件和输出不在暂存区？
- 是否运行了相关测试和完整测试？
- 是否说明了数学假设、评价指标与已知限制？
- 是否给出了提交号、分支名和 Pull Request 链接？
- 是否等待成员审查，而没有自行合并？

## 给 AI 的底线规则

如果仓库状态不清楚、存在未提交修改、出现冲突、测试失败或需要高风险操作，AI 必须停止推进并解释情况。宁可多问一次，也不要覆盖同伴工作、泄露资料或破坏仓库历史。
